Section 02
两个 Skill 的分工

epic-story-doc
设计侧 · 文档生成

Section 03 · 设计侧
生成设计文档
1
打开评审台，复制 Agent 提示词
双击 epic-story-reviewer.html，点击「复制 Agent 提示词」按钮。提示词已包含完整 JSON Schema 和所有输出规则，无需任何补充。
2
粘贴给 Claude，附上需求描述
在提示词末尾直接追加需求描述或现有文档内容。Claude 触发 epic-story-doc skill，同时输出两个文件：
draft_{EpicId}.md     ← 存入 docs/ 目录，提交 git
draft_{EpicId}.json   ← 用于生成评审页
3
运行 inject.py 生成评审页
在项目根目录执行，inject.py 将数据注入评审台模板，生成自包含 HTML：
python inject.py docs/draft_E8.json
输出文件：review_E8_YYYYMMDD.html，与 draft.json 同目录
💡 Claude Code 自动化
如果使用 Claude Code，可以在对话结束时直接说「运行 inject.py 生成评审页」，Claude Code 会自动执行第 3 步。
Section 04 · 设计侧
评审流程
1
打开评审页，阅读各章节内容
双击 review_E8_YYYYMMDD.html，左侧导航显示所有章节（背景、目标、算法约定等）和 Story，点击跳转。章节内容支持公式（KaTeX）、流程图（Mermaid）、表格渲染。
2
逐 Story 审核
点击左侧 Story 节点进入评审视图。顶部三个投票按钮标记整体状态，任务清单支持移除/新增/内联编辑，每条 AC 独立标记通过/疑问/拒绝。
标记「疑问」或「拒绝」后，右侧面板自动汇聚待处理清单。未填写意见的 AC 默认视为通过。
3
对章节内容添加批注
点击左侧「背景」「核心算法约定」等章节节点，在页面底部批注框填写审核意见，批注会随导出 JSON 一并输出。
4
导出审核 JSON
右下角点击「导出审核 JSON」，同时触发文件下载和复制到剪贴板。可直接粘贴给 Claude 触发重生成，也可保存文件备查。
进度自动保存在浏览器本地，刷新不丢失。
评审操作说明导出字段
AC ✓ 通过保持原内容不变status: "ok"
AC ⚠ 疑问填写疑问内容，重生成时修改该 ACstatus: "q", question: "..."
AC ✕ 拒绝填写拒绝原因，重生成时重写该 ACstatus: "no", question: "..."
未标记 AC默认通过，不影响重生成status: "ok"
任务移除该任务从文档中删除removed: true
任务编辑使用修改后文本modified_text: "..."
新增任务插入对应 Story 末尾added: "..."
章节批注追加到对应章节末尾section_comments[].comment
Section 05 · 设计侧
重生成文档
1
将 review_result.json 粘贴给 Claude
导出时已自动复制到剪贴板，直接粘贴即可。JSON 末尾的 agent_instruction 字段已包含完整指令，Claude 读到后自动触发 epic-story-doc skill 的重生成模式。
2
Claude 输出最终文档
重生成规则自动应用：被拒绝/有疑问的 AC 按意见修改，被移除的任务删除，新增任务插入，章节批注追加，版本号自动递增。
final_E8_v0.2.md     ← 提交 git，作为实施侧真源
final_E8_v0.2.json   ← 可选，存档用
3
提交 git，进入实施阶段
将 final_E8_v0.2.md 提交到 docs/ 目录，这是唯一的设计-实施交接文件。
⚠ 注意
实施侧以 final_{EpicId}.md 为唯一真源，不读 JSON 文件。确保 MD 文件提交到 git 后再通知实施侧开始。
Section 06 · 实施侧
开始实施
1
读完所有 sections 上下文再开始
文档中「背景」「核心算法约定」等章节包含公式、架构图、约束条件，是实施的硬性前提。不允许只看 Story 标题就开干。
sections 中的公式用 $...$ 或 $$...$$ 标注，架构图用 mermaid 代码块。这些是实施约束，不是装饰。
2
确认 Story 顺序，按序执行
Story 之间有依赖关系，按文档顺序执行。当前 Story 所有 AC 通过前，不进入下一个 Story。
3
创建实施记录目录
进入每个 Story 前，在设计文档同级目录创建：
implementation_logs/E8/S1/
├── implementation_plan.md
├── task.md
└── walkthrough.md
4
识别并处理 TBD
文档中 TBD 标记的字段/阈值/接口名，不允许编造，必须停下来 surface 给设计侧。唯一例外：用户在当前对话明确指示假设值，此时 commit 必须注明假设内容和影响范围。
Section 07 · 实施侧
AC → 测试用例
每条 AC 必须对应一个独立测试函数，不允许合并，不允许漏写。
AC 部分测试代码
Given 前提条件fixture / setup / mock 数据准备
When 触发动作被测函数 / 接口的实际调用
Then 预期结果assert 语句（含具体数值）
python
# AC1: 幂等性校验
# Given: 数据库中已存在相同因子记录
# When: 执行 save_adj_factor
# Then: 记录数不增加，返回 False

def test_e8_s1_idempotent_when_factor_unchanged(db_session, seed_adj_factor):
    # Given
    existing_count = db_session.query(StockAdjFactor).count()
    # When
    result = save_adj_factor(ts_code="000001.SZ",
                             adj_factor=seed_adj_factor.adj_factor)
    # Then
    assert result is False
    assert db_session.query(StockAdjFactor).count() == existing_count
✓ 命名规则
test_e{N}_s{M}_{语义描述}，例如：test_e8_s1_idempotent_when_factor_unchanged
Section 08 · 实施侧
Task → Commit
每个 Task 对应一个 commit，不拆不合。commit 完成后在设计文档中将该 Task 标记为 - [x]。
commit
feat(collector): [E8-S1-T2] 实现仅在因子变动时执行 INSERT 的判断逻辑

比对最新库存值与采集值，差值绝对值 < 1e-8 时跳过写入，返回 False。
影响 save_adj_factor 方法，幂等性由 AC1 测试覆盖。
type适用场景
feat新功能实现
fixBug 修复
test测试用例新增/修改
refactor重构，不改变行为
chore配置、脚本、TBD 假设记录
docs文档更新、任务勾选回填
Section 09 · 实施侧
Story 完成条件
✓
全部 AC 测试通过
每条 AC 对应的测试函数均通过，无跳过，无空 assert。
✓
设计文档全部 Task 勾选
final_{EpicId}.md 中本 Story 的所有 - [ ] 均已更新为 - [x]。
✓
产出 walkthrough.md
保存到 implementation_logs/E8/S1/walkthrough.md，必须包含物理真源证据（SQL 结果 / 日志片段），100% 覆盖设计文档中的 AC。
✓
更新 IMPLEMENTATION_FEEDBACK.md
在 docs/IMPLEMENTATION_FEEDBACK.md 将本 Story 状态更新为 DONE。
⚠ 强制规则
任何一条 AC 测试未通过，本 Story 不算完成，不能进入下一个 Story。walkthrough 必须含物理证据，纯文字描述无效。
Section 10
文件目录约定
docs/
  ├── draft_E8.md  ← 设计侧初稿（提交 git）
  ├── draft_E8.json  ← 评审台加载用（提交 git，可选）
  ├── final_E8_v0.2.md  ← 评审后重生成（提交 git，实施侧真源）
  ├── IMPLEMENTATION_FEEDBACK.md  ← Story 全局状态索引
  ├── TABLES_INDEX.md  ← 字段/表结构索引
  └── implementation_logs/
      └── E8/
          ├── S1/
          │   ├── implementation_plan.md
          │   ├── task.md
          │   └── walkthrough.md
          └── S2/ ...

tools/  ← 评审工具，不进业务代码目录
  ├── epic-story-reviewer.html  ← 评审台模板
  └── inject.py  ← 注入脚本

review/  ← 评审产物，不进 git
  ├── review_E8_20260514.html  ← inject.py 输出
  └── review_result_E8.json  ← 评审台导出（可选存档）
💡 .gitignore 建议
将 review/ 目录加入 .gitignore，评审产物不进版本库。docs/draft_*.json 视团队协作需求决定是否提交。
Section 11
常见问题
Q
评审台导出的 JSON 存到哪里？
导出时同时触发浏览器下载（默认落到 ~/Downloads）和复制到剪贴板。推荐流程：直接粘贴给 Claude 触发重生成，不需要手动移动文件。如需存档，建议保存到 review/ 目录，不提交 git。
Q
文档里有 TBD，实施侧要怎么处理？
停止该 Task，在 task.md 标注卡点，在 IMPLEMENTATION_FEEDBACK.md 标记「暂停」，surface 给设计侧。禁止编造默认值继续。唯一例外：用户明确指示假设值，此时 commit 必须注明假设内容和影响范围。
Q
Story 没有 AC 怎么办？
默认拒绝实施，要求设计侧补 AC。如果能从 Task 描述推出明确的 Given-When-Then，可以主动补全 AC 并提交给设计侧 review。紧急任务且设计侧已批准时，标注「无 AC」实施并在事后补一份 AC。
Q
评审进度关闭浏览器后还在吗？
评审台使用 localStorage 自动保存，关闭后重新打开同名 HTML 文件可恢复进度。不同浏览器或设备之间不共享，建议在同一台机器上完成评审。
Q
inject.py 找不到模板怎么办？
inject.py 默认在自身所在目录查找 epic-story-reviewer.html。确保两个文件在同一目录（推荐都放 tools/ 目录）。也可以手动指定模板路径：
python inject.py draft_E8.json tools/epic-story-reviewer.html

# 知识库：股票 K 线与复权数据处理规范

## 1. 数据存储标准 (ODS 层)
为了兼顾数据原始性与计算准确性，系统采用“原始价 + 独立因子”的存储架构。

### 1.1 K 线数据 (`stock_kline_daily`)
*   **口径**：**不复权 (Unadjusted)**。
*   **字段定义**：`close`, `high`, `low`, `open` 等均存储交易所公布的原始成交价。
*   **意义**：保留历史成交的真实价位和量价关系，作为最基础的数据资产，永不随分红变动。

### 1.2 复权因子 (`stock_adjust_factor`)
*   **口径**：**累积后复权因子 (Cumulative Backward Factor)**。
*   **存储逻辑**：仅记录“变动事件”。若某日无分红送转，则该日无新记录。
*   **查询方式**：查询某日有效因子时，需使用 `ORDER BY adjust_date DESC LIMIT 1` 获取该日期及之前的最后一条记录。

---

## 2. 复权计算逻辑 (ADS 层)
在进行跨周期对比（如新高/新低计算）时，必须统一使用 **前复权 (Forward Adjustment)** 逻辑。

### 2.1 前复权公式
$$\text{P}_{adj} = \text{P}_{raw} \times \frac{\text{F}_{date}}{\text{F}_{latest}}$$
*   $\text{P}_{adj}$：前复权价。
*   $\text{P}_{raw}$：当日原始价。
*   $\text{F}_{date}$：当日对应的累积因子。
*   $\text{F}_{latest}$：当前最新的累积因子（锚点）。

### 2.2 性能优化建议
*   **避免 SQL 大表关联**：由于 MySQL 5.7 不支持窗口函数且 A 股全市场（5000+股）250 日窗口数据量较大（125万+行），建议在 Python 层进行内存计算。
*   **内存计算流程**：一次性读取窗口内所有 K 线与相关因子，使用 `bisect` 算法快速匹配日期因子，在内存中完成对比。

## 3. 多数据源备份 (Tushare 降级)
当主数据源 (BaoStock) 出现连接问题或数据滞后时，启用 Tushare 作为备份。

### 3.1 Tushare 适配
*   **K 线接口**：使用 `/api/v1/stock/daily`。注意 Tushare 的 `pct_chg` 是百分比格式（如 9.9），入库前需除以 100。
*   **因子接口**：使用 `/api/v1/stock/adj_factor`。其返回的 `adj_factor` 与 BaoStock 的后复权因子口径一致，可直接混用。
*   **调用规范**：通过 `tushare-api` 微服务调用，避免本地包路径冲突。

## 4. 常见问题 (FAQ)
*   **Q: 为什么新高家数为 0？**  
    A: 通常是因为 `stock_adjust_factor` 缺失了最新交易日的因子，导致前复权公式中的 $\text{F}_{latest}$ 错误。需检查定时任务是否补齐了最近三天的因子。
*   **Q: 为什么 1900 万数据不需要重下？**  
    A: 因为我们采用了动态复权逻辑。只要因子表完整，原始 K 线永远有效，只需在计算时动态乘以因子即可。

# A 股个股基本面分析系统 - 工程技术方案

> 版本:v0.1 · 日期:2026-05-09 · 状态:初稿

---

## 背景

A 股市场有 5300+ 只股票,人工无法全覆盖深度研究。教科书式基本面框架(七维度均匀打分、雷达图、大而全报告)在 A 股有几个结构性失灵点:

1. **政策被误用为加分项**:政策驱动 ≠ 长期超额收益(光伏、新能车、半导体三个反例),政策真正应当作为"产能投放预测"和"业绩扰动评估"的输入,而不是独立维度
2. **缺预期差维度**:基本面优秀 + 预期已 price-in = 不涨甚至跌,A 股是预期博弈市场不是 DCF 市场
3. **缺财务戳穿层**:A 股年报叙述性内容很多是公司包装,必须用财务勾稽反向验证
4. **跨行业打分掩盖差异**:不同行业关键指标完全不同,均匀权重打分会稀释关键信号
5. **静态研究无法应对轮动**:A 股是周期性轮动 + 风格切换市场,需要"行业认知池"做存量积累,以便切换时快速反应

现有研究链路(从年报通读开始 → 找数据 → 写报告)效率低,信息搜集臃肿但研究判断不锋利。需要用工程化方法把研究员从苦力活中解放出来,把覆盖能力从 30 只放大到 300 只。

## 目标

**总体定位**:AI 把研究员的覆盖能力放大,系统输出"决策辅助卡片",最终判断和决策留给人。

**可量化目标**:

| 指标 | 当前 | 目标 |
|---|---|---|
| 深度跟踪标的数量 | ≤30 只 | ≥200 只 |
| 排雷扫描频率 | 手动不定期 | 全市场每周一次 |
| 财报/公告响应时延 | 数天 | ≤24h 自动重算 |
| 行业覆盖深度 | 1-2 个粗略 | 2 个深度 + 3-5 个浅覆盖 |
| 单只个股深度分析耗时 | 半天-一天 | ≤30 分钟(看卡片+点核心数据) |

## 范围

**第一阶段覆盖行业**:
- **半导体**(申万二级:半导体)—— 设备、材料、设计、制造、封测、IP 全产业链
- **生物合成**(自定义概念,跨多个申万行业)—— 合成生物学相关公司,涉及生物制造、化工、医药、新材料

**系统层次**:数据层 → 排雷层 → AI 抽取层 → 财务验证层 → 同业对比层 → 触发跟踪层 → 输出层 共 7 层。

## 非目标

**明确不做的事**(避免范围蔓延):

- ❌ **不做行情/股价预测** —— 系统只做基本面分析,不输出"买入/卖出"信号
- ❌ **不做自动交易** —— 不接券商接口,不做下单
- ❌ **不做 DCF 估值模型** —— 只做估值"相对位置"判断(行业分位、历史分位)
- ❌ **不做投资组合管理** —— 只对单只个股输出认知
- ❌ **不做 Web 多用户系统** —— 单人本地使用,不做权限、登录、协作
- ❌ **不做实时行情推送** —— 只在基本面相关事件触发时响应,不做盘中实时
- ❌ **不做美股/港股覆盖** —— 第一阶段只 A 股(港股映射可在 L7 输出层做关联展示,不做独立分析)
- ❌ **不替代研究员判断** —— 系统输出的所有结论标注"可信度"和"原文溯源",最终判断由人做
- ❌ **不做行业全景的全市场推广** —— 只做半导体 + 生物合成,其他行业等 MVP 跑通再扩

## 假设与约束

- **使用者**:个人(单用户)
- **部署**:腾讯云服务器(主)+ 家中内网服务器(备/开发)
- **技术栈**(承袭 userPreferences):
  - 数据库:MySQL 5.7 + ClickHouse 双写
  - 编程语言:Python(3.11+)
  - 数据源:Tushare Pro(主)+ akshare(辅)+ 巨潮资讯网爬虫
  - AI 模型:Anthropic Claude API(Sonnet 4.6 主力 + Opus 4.7 关键判断)
- **预算约束**:AI 月度调用预算 ≤ ¥1000(TBD,根据实际调用量调整)
- **时间约束**:MVP 总工期 ~11 周

## 项目基座现状 (Existing Infrastructure)

本系统并非从零构建，而是基于已有的 **microservice-stock** 腾讯云生产环境扩展：

- **数据采集**: `tushare-api` (P0)、`akshare-api` (P2) 已稳定运行。
- **调度系统**: `stock-manager-api` 已具备成熟的 `APScheduler` 任务流及 `meta_data_readiness` 数据就绪契约机制。
- **存储层**: MySQL 5.7 (元数据) + ClickHouse (行情/明细) 双写架构已就绪。
- **标准化**: `ts_code` 归一化、`pct_chg` 小数化等口径已在全仓强制执行。

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|---|---|---|---|
| Tushare 接口限频或调整 | 高 | 中 | akshare 双源 + 失败重试 + 自建数据源缓存 |
| AI 抽取幻觉 | 高 | 高 | 强制 source_quote 溯源 + Schema 校验 + 数值合理性检查 + 财务交叉验证 |
| 巨潮反爬 | 中 | 中 | 降频抓取 + UA 轮换 + 失败兜底人工 |
| AI 调用成本超预算 | 中 | 中 | 模型分层(Sonnet 主力)+ 强缓存 + 月度成本监控自动告警 |
| 财报口径变化(会计准则) | 中 | 中 | 调整层抽象 + 关键变更人工标注 + 文档维护 |
| 触发器噪音失控 | 中 | 中 | 触发器优先级 + 频率上限 + 早期 dry-run 验证 |
| 个人精力不足导致烂尾 | **高** | **高** | **严格 MVP 切片,每 2-3 周一个里程碑,跑通一个再做下一个;不堆功能** |
| 系统建好后未使用 | 高 | 中 | 用决策辅助效率作为 KPI,与现有研究流程紧密耦合,定期 review 实际使用情况 |

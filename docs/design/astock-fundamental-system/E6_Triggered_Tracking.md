# E6 触发式跟踪

让系统"动态"起来的核心,**触发式架构而非定时全量**。预计耗时 1.5 周。

## E6-S1 触发源监控

**作为** 系统使用者,**我希望** 关键事件被实时捕获,**以便** 系统能快速响应。

### 任务

- E6-S1-T1 公告触发源(监控巨潮、深交所、上交所)
- E6-S1-T2 财报触发源(基于披露日历预判 + 实时验证)
- E6-S1-T3 行情异动触发源(单日涨跌幅、放量、连续 N 日异动)
- E6-S1-T4 卖方研报突增监控(TBD,需要研报数据源)

### 验收标准

- **AC1**: 公告捕获时延
  - **Given** 某研究池股票发布业绩快报公告
  - **When** 公告在巨潮发布
  - **Then** 系统在 30 分钟内捕获并写入 `meta_trigger_events` 表

- **AC2**: 行情异动识别
  - **Given** 收盘后行情数据已同步
  - **When** 触发 `detect_price_anomaly.py`
  - **Then** 单日涨跌幅 > 5% 或换手率 > 历史 P95 的研究池股票被记录到触发事件表

## E6-S2 触发器规则与优先级

**作为** 系统使用者,**我希望** 触发器有优先级控制,**以便** 不会被噪音淹没。

### 任务

- E6-S2-T1 设计触发器规则(事件类型 → 优先级 → 重算范围)
- E6-S2-T2 优先级队列实现(高优先级立即处理,低优先级合并批处理)
- E6-S2-T3 触发器去重(同一公司 24 小时内多次触发同类事件,合并为一次重算)

### 触发器规则(初版)

| 事件类型 | 优先级 | 重算范围 |
|---|---|---|
| 年报披露 | 高 | 全量重算(L3+L4+L5) |
| 季报披露 | 中 | 财务字段重算(L4) |
| 业绩预告 | 中 | 财务字段更新 + 风险卡片重生成 |
| 调研纪要 | 低 | L3 抽取增量 |
| 行情异动 | 低 | 仅记录,不重算(供 L7 输出层展示) |
| 关联交易公告 | 高 | L4 触发 R006 重算 |
| 大股东减持 | 中 | L2 排雷指标重算 |
| 商誉减值预告 | 高 | L4 触发 R007 重算 |

### 验收标准

- **AC1**: 优先级处理
  - **Given** 任务队列同时有 1 条年报披露(高)和 5 条调研纪要(低)
  - **When** worker 取任务
  - **Then** 年报披露任务先处理,5 条调研纪要在年报处理完后批处理

- **AC2**: 去重
  - **Given** 同一公司 24 小时内发布 3 份调研纪要
  - **When** 触发抽取
  - **Then** 系统合并为 1 次抽取任务(批量处理 3 份纪要),节省 API 调用

## E6-S3 任务队列与异步重算

**作为** 系统架构维护者,**我希望** 重算任务异步执行,**以便** 触发不阻塞数据接入。

### 任务

- E6-S3-T1 (REUSE) 现有的 `meta_pipeline_run` 与 `meta_data_readiness` 表进行状态跟踪。
- E6-S3-T2 实现 worker 进程池(默认 3 个 worker)处理 AI 抽取等长耗时任务。
- E6-S3-T3 失败任务重试 + 死信队列(失败 3 次进入人工复核)

### 验收标准

- **AC1**: 异步执行
  - **Given** 触发事件入队
  - **When** worker 异步处理
  - **Then** 数据接入流程不被阻塞,worker 在 5 分钟内开始处理任务

- **AC2**: 重算时延
  - **Given** 一份新年报触发全量重算
  - **When** 任务进入队列
  - **Then** L3 抽取 + L4 验证 + L5 对比全部完成时间 ≤ 24 小时(主要瓶颈是 AI 抽取)

## 二、按「想要什么产出」反查提问方式

### 想要快速判断 / 决策辅助
> 「我在 A 和 B 之间犹豫,A 的好处是 X,B 的好处是 Y,你怎么看」
> 「这个 TBD 该怎么销账」

→ 不要用「写一下」「实现一下」,会触发 skill 直接出文档,跳过讨论。

### 想要可交付的代码或文档
> 「直接出方案」「写完整版」「上代码」

→ 必须明确说,否则 Claude 默认先讨论,不会直接出。

### 想要观点交锋,不要文档
> 「你觉得呢」「质疑一下我的思路」「找我方案的漏洞」「假装是 reviewer 来挑刺」

→ 这种问法会让 Claude 直接进入对话模式,不会启动 skill。

### 想要可视化
> 「做一个 X 页面」「画个 X 图」「可视化 X 数据」

→ 自动触发 obsidian-amber-design,深色研报风。如果想要别的风格,**必须明说**(亮色 / Material / 极简等)。

### 想要长程任务推进
> 「先讨论方向,你别急着出代码」+ 第二轮 「OK 现在开始写」

→ 分两步走最稳。第一轮限制 Claude 不出文档,第二轮触发可交付物。

## 三、Style 选择对照(Claude.ai 设置层)

`userPreferences` 已经做的事(全局生效):
- 中文回答
- 直接给结论,不要铺垫
- 多观点列权衡
- TBD 标清楚不编造
- 工程师视角

`userStyle` 是更上一层的开关(优先级高于 userPreferences),但你目前没设。可以考虑的几种:

| Style 候选 | 适用场景 | 跟当前 userPreferences 的关系 |
|---|---|---|
| **保持默认(无 style)** | 大部分场景 | userPreferences 已经够用 |
| **Concise / 简洁版** | 快速问答、灵感碰撞、闲聊 | 会让回答更短,可能损失 trade-off 表 |
| **Explanatory / 详尽版** | 学习新领域、系统性理解 | 跟 userPreferences「直接给结论」轻微冲突,会变啰嗦 |
| **Formal / 正式版** | 给团队 / 客户的正式文档 | 这个项目是个人开发,用不上 |
| **自定义 style** | 特殊场景独立设置 | 见下文 |

### 我的建议:不切 style,保留默认

理由:
1. 你的 `userPreferences` 已经是定制化的「Concise + 工程师视角」,内置 style 反而会冲突
2. 自定义 style 的 ROI 在你这个项目不高 —— skill 已经覆盖了主要产出场景
3. 真要某次对话风格变化,直接在 prompt 里说就行(「这次先简短,只要核心结论」)

### 如果非要做自定义 style,可考虑两个

#### Style A:「探讨模式」
```
默认进入观点交锋,不出代码、不写完整文档、不调用任何 skill。
即使我提到「写」「设计」「做」这类词,也优先理解为「讨论怎么写/设计/做」。
要触发产出,我会明确说「直接出方案」「上代码」「写完整版」。
```

适合:概念早期阶段、方案推演、决策辅助多的对话

#### Style B:「实施模式」
```
默认信任我的判断,跳过澄清,直接出可交付物。
按 epic-story-doc / astock-sql-design / obsidian-amber-design 的 skill 输出。
不要问「先讨论方向吗」,直接交付。
```

适合:已经讨论清楚、进入产出阶段的对话

但注意:**这两个 style 互斥,不能同时启用**。我个人不推荐固化,因为同一个项目里两种状态都会出现,切来切去成本高。

## 四、对话节奏控制(单轮内)

### 想要 Claude 多想一会再答
> 「先想清楚再回答」「你先列出几种可能性,再选一个推荐」

### 想要 Claude 主动 challenge 你
> 「假装是 senior engineer 在 review,挑这个方案的毛病」
> 「找出我没想到的反方理由」

### 想要 Claude 短促精准
> 「一句话总结」「就回答 yes/no + 一行理由」

### 想要 Claude 终止当前任务转向新方向
> 「不写了,我们换个话题:...」
> 「停下,先回答这个问题:...」

如果 Claude 没听话,可能是 skill 触发太强,直接说「这次不要触发任何 skill」即可关闭。

## 五、什么时候改 userPreferences vs Style vs 加 skill

| 想改的事 | 改哪里 |
|---|---|
| 全局回答风格(语言 / 简洁度 / 视角) | `userPreferences` |
| 单次对话的临时风格(「这次详细点」) | 直接在 prompt 里说 |
| 某类任务的固定输出格式 | 加 skill |
| 某类任务的固定上下文(项目知识) | project knowledge |
| 跨项目的全局开关(很少用) | `userStyle` |

你的项目目前 `userPreferences` + 4 个 skill + project knowledge 的组合已经覆盖得很完整,**不需要再加 userStyle**,这是最优配置。

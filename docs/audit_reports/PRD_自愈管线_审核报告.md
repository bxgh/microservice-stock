# PRD 架构审计报告：自愈型数据管线 (v1.1)

**审计人**: Antigravity [Requirement Architect & Data Quality Steward]
**审计对象**: `docs/design/数据管线/PRD-自愈型数据管线.md` (v1.1)
**审计结论**: 整体架构逻辑自洽，闭环完整。但在**并发安全、第三方数据源特性约束、以及回滚级联**等深水区存在 4 处“隐性地雷”，需要在进入开发前（Implementation Plan 阶段）进行防御性设计补充。

---

## 致命缺陷 (CRITICAL)

### 1. 仲裁矩阵的“同源污染”盲区 (Correlated Error Risk)
*   **PRD 设定**：当 `P1 == P2 != P0` 时，以 P1/P2 为准覆盖 P0。
*   **审计发现**：BaoStock(P1) 和 AkShare(P2) 在某些非核心字段（如流通市值）上，可能底层都抓取自同一个免费网页（如新浪财经/东方财富）。如果该网页出错，P1和P2会表现出“高度一致的错误”，从而联手把本是正确的 Tushare(P0) 数据给覆盖掉。
*   **整改建议**：增加**“偏离度极值熔断”**。如果 P1/P2 与 P0 的偏差超过阈值（如价格偏差 > 10%），**严禁自动覆盖**，必须转为人工作业（报 ERROR）。自愈系统只能修复“微小漂移”或“明确的除权错误”。

### 2. 复权因子的“三源不可比”陷阱 (Incomparable Factors)
*   **PRD 设定**：对 `stock_adjust_factor` (P0级) 进行三源对账。
*   **审计发现**：不同数据商的复权因子（Adj Factor）**基准日和计算公式完全不同**。Tushare 的因子和 BaoStock 的因子在绝对值上是没有可比性的。
*   **整改建议**：对 `stock_adjust_factor` 取消“横向三源对账”，改为**“纵向逻辑审计”**（例如：前复权因子随时间推移**绝对不可能变小**，如果 T 日因子 < T-1 日因子，则100%是数据错乱，直接触发 Tushare 接口重刷）。

---

## 高风险 (HIGH)

### 3. ClickHouse 同步的“竞态条件” (Race Condition)
*   **PRD 设定**：自动补数 -> 触发 MySQL to CK 同步 -> 触发下游重算。
*   **审计发现**：ClickHouse 的增量同步（通过 `syncer.py`）是一个**耗时的异步过程**。如果发出同步指令后，未等待 CK 端返回 `ACK (同步完成确认)` 就立刻下发了 `recalc_signal`，内网 Node-41 的重算任务读到的依然是旧数据。
*   **整改建议**：Stage F 必须是**阻塞型等待**或基于回调的设计。必须查询内网 CK 的 `meta_data_readiness` 确认 T 日数据已落盘，才能释放重算信号。

### 4. 回滚引发的“二次脏数据” (Rollback Cascade Problem)
*   **PRD 设定**：提供 API 恢复 `before_data`，并清理重算信号。
*   **审计发现**：如果自愈系统错误地修改了数据，且下游 ADS 已经完成了重算。此时调用 API 回滚了 ODS 表，但 ADS 表里依然保留着由“错误 ODS”算出来的指标。仅仅“清理重算信号”是不够的。
*   **整改建议**：回滚操作（Rollback）必须被视为**一次新的自愈事件**。回滚 ODS 后，必须**再次触发级联失效和重算信号**，让下游 ADS 根据“回滚后的正确原始数据”再重算一次。

---

## 优化建议 (MEDIUM)

### 5. 级联失效的“爆炸半径”控制 (Blast Radius)
*   **PRD 设定**：ODS 修复触发 ADS 清理。
*   **审计发现**：如果深度扫描器发现了一年前（T-365天）的 K 线错误并修复了它，按照逻辑，它会把这一年来所有的 MA/MACD 全部作废重算。这会消耗巨大算力。
*   **整改建议**：引入“时间衰减过滤”。对于发生在 1 年前的轻微数据修正，可以选择**“不进行级联重算”**，以节省计算资源，仅修正 ODS 底表。

# 03. 内网计算引擎 (Core Engine Specification)

> **核心职责**: 历史数据存储加速、策略回测计算、因子挖掘。
> **部署位置**: 内网高性能服务器 (10C 64G)

## 1. ClickHouse 存储加速层架构

ClickHouse 是本系统的**性能倍增器**。通过 T+1 的同步机制，将云端 MySQL 的行式数据转换为列式数据，供回测引擎高速读取。

### 1.1 核心数据模型设计 (Schemas)

真正的量化系统需要通过不同的存储策略来处理不同特性的数据。

#### A. 标准行情: `kline_day` (日/周/月线)
*   **特性**: 结构固定，查询频率极高。
*   **策略**: **MergeTree**。

```sql
CREATE TABLE stock_dw.kline_day
(
    `code` String CODEC(ZSTD(1)),
    `trade_date` Date CODEC(Delta, ZSTD),
    `open` Float32 CODEC(ZSTD),
    `high` Float32 CODEC(ZSTD),
    `low` Float32 CODEC(ZSTD),
    `close` Float32 CODEC(ZSTD),
    `volume` UInt64 CODEC(ZSTD),
    `amount` Float64 CODEC(ZSTD),
    `turnover` Float32,
    `pct_chg` Float32
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(trade_date)
ORDER BY (code, trade_date)
SETTINGS index_granularity = 8192;
```

#### B. 高频数据: `tick_snapshot` (分笔/快照)
*   **特性**: 数据量极大 (每天亿级)，写多读少。
*   **优化**: 使用 `LowCardinality` 优化字符串，使用 `Delta` 压缩时间戳。**严禁存入 MySQL**。

```sql
CREATE TABLE stock_dw.tick_snapshot
(
    `code` LowCardinality(String),
    `created_at` DateTime64(3) CODEC(Delta, ZSTD), -- 精确到毫秒
    `price` Float32,
    `vol` UInt64,
    `ask1` Float32, `bid1` Float32,
    `ask1_vol` UInt64, `bid1_vol` UInt64,
    -- ... ask2-5, bid2-5 省略 ...
    `type` Enum8('买盘'=1, '卖盘'=2, '中性'=0)
)
ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(created_at) -- 按日分区，方便过期删除
ORDER BY (code, created_at)
TTL created_at + INTERVAL 6 MONTH;  -- 只保留6个月的一级数据
```

#### C. 基本面数据: `finance_report` (季报)
*   **特性**: 字段超多 (100+)，更新低频，常有 Text 备注。
*   **策略**: 使用 `ReplacingMergeTree` 自动去重（修正财报时覆盖旧版）。

```sql
CREATE TABLE stock_dw.finance_report
(
    `code` String,
    `report_date` Date,      -- 报告期 (2023-09-30)
    `pub_date` Date,         -- 发布日 (2023-10-25)
    
    -- 核心财务指标
    `eps` Float32,           -- 每股收益
    `nav_ps` Float32,        -- 每股净资产
    `roic_yearly` Float32,   -- 年化ROIC
    `net_profit_yoy` Float32,-- 净利同比
    
    -- 扩展字段 (留存复杂JSON)
    `raw_json` String CODEC(ZSTD(3))
)
ENGINE = ReplacingMergeTree(pub_date) -- 以后发布的数据为准
PARTITION BY toYYYY(report_date)
ORDER BY (code, report_date);
```

#### D. 因子库: `factor_daily` (宽表)
*   **特性**: 列数随策略增加动态扩张。
*   **策略**: 垂直切分，不同类别的因子存不同表，或使用 `Map` 类型。

```sql
CREATE TABLE stock_dw.factor_daily
(
    `code` String,
    `trade_date` Date,
    `factors` Map(String, Float32) -- 灵活存储 {'ma5': 10.2, 'rsi': 60.5}
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(trade_date)
ORDER BY (code, trade_date);
```

### 1.2 性能基准 (Benchmark)

| 查询场景 (Scope) | 涉及行数 (Rows) | MySQL 耗时 | ClickHouse 耗时 | 加速比 |

## 2. 数据同步服务 (MySQL -> ClickHouse)

这是一个仅在内网运行的**ETL Worker**。

### 2.1 同步逻辑 (Python Snippet)

```python
def sync_increment_data(target_date: str):
    """T+1 增量同步逻辑"""
    
    # 1. 提取 (Extract) from MySQL
    # 使用流式游标 (SSCursor) 防止内存溢出
    mysql_cursor.execute(
        "SELECT code, trade_date, open, ... FROM kline_day WHERE trade_date = %s",
        (target_date,)
    )
    
    # 2. 转换 (Transform)
    batch_data = []
    while True:
        rows = mysql_cursor.fetchmany(10000)
        if not rows: break
        # 这里可以加入简单的数据清洗清洗逻辑 DQC
        batch_data.extend(rows)
    
    # 3. 加载 (Load) to ClickHouse
    if batch_data:
        client.execute(
            "INSERT INTO stock_dw.kline_day VALUES",
            batch_data,
            types_check=True
        )
        print(f"Synced {len(batch_data)} rows for {target_date}")
```

使用 Linux Crontab 管理：

## 3. 策略引擎集成 (Backtrader + ClickHouse)

为了利用 ClickHouse 的速度，我们需要重写 Backtrader 的数据加载器。

### 3.1 `ClickHouseDataFeed` 实现

```python
import backtrader as bt
import pandas as pd
from clickhouse_driver import Client

class ClickHouseData(bt.feeds.PandasData):
    """
    直接从 ClickHouse 加载 Pandas DataFrame
    """
    params = (
        ('datetime', 'trade_date'),
        ('open', 'open'),
        ('high', 'high'),
        ('low', 'low'),
        ('close', 'close'),
        ('volume', 'volume'),
        ('openinterest', -1),
    )

def load_data_from_ch(code, start_date, end_date):
    client = Client('localhost')
    query = f"""
    SELECT trade_date, open, high, low, close, volume 
    FROM stock_dw.kline_day 
    WHERE code = '{code}' 
      AND trade_date BETWEEN '{start_date}' AND '{end_date}'
    ORDER BY trade_date
    """
    # 直接转为 DataFrame，速度极快
    df = client.query_dataframe(query)
    df['trade_date'] = pd.to_datetime(df['trade_date'])
    df.set_index('trade_date', inplace=True)
    return df
```

## 4. 资源隔离：Ephemeral Docker Worker

为了防止策略内存泄漏，采用**"用完即焚"**的容器策略。

### 4.1 启动指令 (Run Command)

当 Redis 收到回测任务时，内网的主控进程 (Dispatcher) 会执行：

```bash
docker run \
  --rm \                                # 任务结束自动删除容器
  --name strategy-task-${TASK_ID} \     # 唯一容器名
  --network host \                      # 使用 Host 网络直连 ClickHouse
  --memory 4g --memory-swap 4g \        # 强制内存封顶 4G，防泄漏
  -v /data/logs:/app/logs \             # 挂载日志目录
  -e TASK_PARAMS='{...}' \              # 注入策略参数
  stock-strategy-runner:latest \        # 镜像名
  python run_backtest.py
```

此方案确保了：即使用户写了一个死循环 `while True: list.append(...)`，也只会 OOM 杀掉该临时容器，**绝不会影响内网服务器的主体稳定性**。

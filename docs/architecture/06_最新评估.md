## 一、对"ts_code 归一化"的精准定位

经过核实，项目中存在**两个层面**的"代码处理"，必须区分清楚：

### 层面 A：值的归一化（已经做对）

**位置**：`baostock-api/services/baostock_service.py`、`wxch-gateway/services/quote_service.py` 等

**作用**：把不同数据源的格式统一到标准 TS_CODE
```
输入：sh.600519 / 600519 / 600519.SH
输出：统一为 600519.SH
```

✅ **这部分做得好，保留即可。**

### 层面 B：数据库字段命名（存在不一致，建议统一）

**问题**：同一个概念（股票代码），在不同表里命名不同：
- 大多数表：`ts_code VARCHAR(20)`
- 部分表：`stock_code VARCHAR(20)`（stock_analyst_rank、stock_health_ledger、CCI_*、stock_sentiment_daily）
- 个别表：`code VARCHAR(16)`（stock_adjust_factor、stock_industry_sw、mootdx_symbol）

**问题定位**——值已经归一化了，但字段名没统一。

### 层面 B 的真实危害

```sql
-- 想要的查询（理想）：
SELECT k.close, l.net_buy_amt
FROM stock_kline_daily k
JOIN stock_lhb_daily l USING (ts_code, trade_date)

-- 实际不得不写（现实）：
SELECT k.close, l.net_buy_amt
FROM stock_kline_daily k
JOIN stock_lhb_daily l 
  ON k.code = l.ts_code 
 AND k.trade_date = l.trade_date
```

**每个 JOIN 都要记不同表用什么字段，写 SQL 时出错率高，性能也差**（不同字段长度的隐式转换）。

### B 类问题的处理建议（**重点**）

不必激进重构整个数据库，分级处理：

**P0（必须做）：新代码层面的统一**

所有**新写的代码**（包括 service.py 的 INSERT/SELECT）：
- 一律使用 `ts_code` 字段名
- 不允许混用 `stock_code` / `code`

**P1（应该做）：发现 service 层的 bug**

我看到一个真实 bug：`information_service.py` 写 `stock_performance_forecast` 时用了 `stock_code` 字段，但表实际字段是 `ts_code`，**这条 INSERT 应该一直在报错或写不进去**。Gemini 修复时务必检查。

**P2（渐进做）：旧表的字段重命名**

按使用频率分批迁移：
1. 高频核心表先做：`stock_kline_daily.code` → `ts_code`（最重要）
2. 其他表跟随：`stock_analyst_rank.stock_code` → `ts_code`
3. 边缘表保持现状即可

迁移方式（每张表）：
- Step 1: ADD COLUMN `ts_code` 复制 `code` 数据
- Step 2: 业务代码切换查询到 `ts_code`
- Step 3: DROP 旧字段

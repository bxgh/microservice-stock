# 量化系统架构深度优化与风险治理 (Architecture & Risk Governance)

本文档旨在针对混合云架构（ClickHouse + MySQL）进行深度的风险排查与机制优化，重点解决**数据质量、系统容错、即时计算**三大核心挑战。

## 1. 核心风险治理矩阵

| 风险域 | 潜在问题 | 严重性 | 治理方案 (Architecture Strategy) |
|--------|---------|--------|-----------------------------------|
| **数据质量** | 源端数据异常（如价格跳变、复权错误）导致策略误判 | 🔴 Critical | **Pre-Ingest DQC (入库前质检)** 管道 |
| **实时计算** | ClickHouse T+1同步无法支撑盘中(Intraday)策略 | 🔴 Critical | **Lambda架构**: Redis(热) + ClickHouse(冷) |
| **网络抖动** | 内网直连云端MySQL/ClickHouse中断导致回测失败 | 🟠 High | **本地Parquet兜底** (Local Fallback) |
| **计算隔离** | 单个策略内存泄漏/死循环拖垮整个Worker节点 | 🟠 High | **Ephemeral Docker Worker** (一次性容器) |

## 2. 数据质量防护体系 (DQC System)

在数据写入 ClickHouse 和 MySQL 之前，必须通过严格的质量关卡。

### 2.1 校验规则集 (Validation Rules)

所有的 K 线数据必须满足：
1.  **完整性**: `Open, High, Low, Close, Volume` 非空。
2.  **逻辑性**: `High >= Low`, `High >= Open`, `High >= Close`, `Low <= Open`, `Low <= Close`。
3.  **波动性**: `|Close - PreClose| / PreClose < 0.25` (除新股外，单日涨跌幅不应离谱，防止拆股未复权)。
4.  **成交量**: `Volume >= 0`。

### 2.2 实施方案 (Data Pipeline)

```python
def validate_kline(df: pd.DataFrame) -> bool:
    """
    数据质检函数，返回是否通过。
    失败的数据会被隔离到 'quarantine_data' 表，报警人工处理。
    """
    # 1. 逻辑校验
    if not (df['high'] >= df['low']).all():
        log_error("DQC_FAIL: High < Low detected")
        return False
        
    # 2. 价格跳变检测 (阈值 25%)
    df['pct_chg'] = df['close'].pct_change()
    if (df['pct_chg'].abs() > 0.25).any():
        log_warning("DQC_WARN: Price surge detected, pending review")
        # 可能是除权缺口，需二次校验
        
    return True
```

## 4. 计算资源隔离：Ephemeral Workers

为了防止"烂策略"搞挂服务器，不再直接运行 Python 进程，而是封装为 Docker 任务。

### 4.1 运行流
1.  内网主控进程监听到 Redis 任务 `task_id: 1001`。
2.  主控进程调用 Docker API：
    ```bash
    docker run --rm \
      --name worker-1001 \
      --network host \
      --memory 4g \
      --cpus 1.0 \
      -v /data/local_cache:/cache \
      stock-strategy-runner:latest \
      python run_backtest.py --task_id 1001
    ```
3.  容器运行结束，自动销毁 (`--rm`)。
4.  **优势**:
    *   **硬限制**: 内存/CPU 严格封顶。
    *   **环境隔离**: 不同的策略可以用不同的 Python 库版本。
    *   **容错**: 容器 Crash 不影响宿主机 Daemon。

## 5. 网络容灾：本地缓存兜底

鉴于内网与云端的连接可能不稳定，建立三级数据读取机制。

### 5.1 读取逻辑 (Pseudo-Code)

```python
class DataProvider:
    def get_data(self, code, start_date):
        # 1. 尝试高速查询 (ClickHouse)
        try:
            return query_clickhouse(code, start_date)
        except ConnectionError:
            log_warn("ClickHouse offline, switching to Local Cache")
            
        # 2. 尝试本地文件 (Parquet) - 每日同步备份
        local_path = f"/data/parquet/{code}.parquet"
        if os.path.exists(local_path):
            return pd.read_parquet(local_path)
            
        # 3. 尝试云端 MySQL (最慢兜底)
        try:
            return query_mysql_cloud(code, start_date)
        except ConnectionError:
            raise SystemError("All data sources unavailable!")
```

### 5.2 实施
*   在内网服务器设置一个 `Cron` 任务，每天夜间（如 02:00），当网络负载低时，静默将云端/ClickHouse 的数据 dump 为 Parquet 文件存储在 160G 硬盘上。
*   这不仅是缓存，也是**冷备份**。

# 01. 体系架构总览 (System Architecture Blueprint)

> **版本**: 2.1 (Multi-Modal & Requirements Aligned)
> **状态**: 已对齐用户硬件现状与业务需求

## 1. 用户需求与约束分析 (User Requirements)

文档基于以下用户明确指定的硬性需求构建：

### 1.1 硬件资源现状 (Hardware Context)
*   **云端服务器**: 腾讯云轻量应用服务器 (2核 4G 80G SSD) —— *资源受限，需充当网关*。
*   **云数据库**: 腾讯云 MySQL (CDB) —— *核心主存储*。
*   **内网服务器**: 本地 Ubuntu (10核 64G 160G HDD) —— *高性能计算节点*。

### 1.2 角色与功能定义 (Roles)
1.  **云端职责**: 必须提供统一 API 入口 (`Cloud-API`)，负责公网流量接入。
2.  **内网职责**: 专注于策略计算 (`Strategy Analysis`)，不直接对外服务。
3.  **前端形态**: 支持微信小程序 (移动端监控) 与 桌面 Web 网页 (深度复盘)。

### 1.3 关键技术约束 (Constraints)
*   **网络限制**: 内网服务器可通过 `Squid Proxy` 访问国内公网，但 **AkShare/BaoStock 等金融数据源访问受限**，因此数据采集必须强制下放到云端执行。
*   **存储加速**: 用户主动提出引入 **ClickHouse** 以解决 MySQL 回测慢的问题。
*   **数据多样性**: 必须处理 Tick 高频数据、财务报表等多种非 K 线数据类型。

---

## 2. 核心架构理念

本系统遵循 **"IO 上云，计算下沉，存储分层"** 的设计哲学，旨在低成本下实现机构级的量化投研能力。

*   **IO 上云 (Cloud Ingestion)**: 利用云服务器的高可用和公网 IP，24小时不间断采集数据，并在公网提供 API 服务。
*   **计算下沉 (Local Compute)**: 利用内网服务器的低成本算力（10核64G），处理回测、因子计算与模型训练等重负载任务。
*   **存储分层 (Tiered Storage)**:
    *   **Hot**: Redis (实时信号/任务状态)
    *   **Warm**: 云端 MySQL (业务主数据/T+0行情)
    *   **Cold/Analytics**: 内网 ClickHouse (海量历史数据/T-1归档)

## 3. 资源规划与配置清单

### 3.1 节点配置明细

| 节点 (Node) | 规格 (Spec) | 成本 (Cost) | 角色定义 | 关键配置约束 |
|:---|:---|:---|:---|:---|
| **Cloud Server** | 2 vCPU / 4GB RAM / 80GB SSD | ~¥60/mo | **流量入口 & 调度中心** | `vm.swappiness=10`<br/>Docker Limit: 3GB Total |
| **Cloud DB** | MySQL 5.7 / 1GB / 50GB | Pay-as-you-go | **主数据源 (SSZT)** | `max_connections=500` |
| **Home Server** | 10 vCPU / 64GB RAM / 160GB HDD | ¥0 (Sunk Cost) | **重计算 & 历史仓库** | ClickHouse 堆外内存: 16GB |

### 3.2 端口与网络规划

> **安全准则**: 内网服务器**完全不暴露公网端口**，所有通信由内网主动发起（Outbound Only）。

| 组件 | 监听地址 | 端口 | 访问源 | 用途 |
|:---|:---|:---|:---|:---|
| **Nginx** | `0.0.0.0` | 80, 443 | 🌏 Any | 公网流量入口 |
| **MySQL (Cloud)** | `0.0.0.0` | 26300 | ☁️ Cloud, 🏠 Home | 核心数据存取 |
| **Redis (Cloud)** | `172.17.0.x` | 6379 | ☁️ Cloud | **不对外** (防攻击) |
| **ClickHouse** | `127.0.0.1` | 8123 | 🏠 Home Only | 回测数据加速 |

*注: 内网连接 Redis 建议通过 Cloud-API 代理，或仅在调试时通过 SSH Tunnel 连接，避免 Redis 直接暴露公网。*

## 5. 核心数据流转图谱 (Data Flow Pipeline)

### 5.1 全景数据采集矩阵 (Data Acquisition Matrix)

针对不同数据类型的更新频率与网络要求，执行严格的**分而治之**策略：

| | 来源 (Provider) | 协议/库 | 采集节点 | 入库路径 | 备注 |
|:---|:---|:---|:---|:---|:---|:---|
| **深度行情** | **L1 Tick 快照** | **Mootdx** | TCP (7709) | **内网 (Home)** | `Mootdx` -> `ClickHouse` | **直连**，流量不走云端，速度最快 |
| **深度行情** | 分时成交 (Transaction) | Mootdx | TCP (7709) | **内网 (Home)** | `Mootdx` -> `ClickHouse` | 同上，盘后补全模式 |
| **基础K线** | 日/周/月线 (前复权) | BaoStock | TCP (Block) | 云端 (Cloud) | `Cloud MySQL` -> `Sync` -> `CH` | 每日16:30定时任务 |
| **基础K线** | **复权因子 / 停复牌** | BaoStock | TCP | 云端 (Cloud) | `Cloud MySQL` -> `CH` | 计算真实收益率必需 |
| **基本面** | **季报/年报 (主表)** | AkShare | HTTP (Eastmoney) | 云端 (Cloud) | `Cloud MySQL` -> `Sync` -> `CH` | 字段多，结构易变，需JSON宽表 |
| **基本面** | 指数成分股权重 | AkShare | HTTP | 云端 (Cloud) | `Cloud MySQL` -> `Redis` | 用于计算Alpha策略基准 |
| **另类数据** | 问财选股 (NLP) | PyWencai | HTTP (Cookie) | 云端 (Cloud) | `Redis` (Cache Only) | 结果不入库，仅做实时过滤 |

### 5.2 差异化流转 Pipeline

#### A. 极速通道 (Tick/Quote)
*   **场景**: 盘中监控、高频因子落地。
*   **链路**: `通达信服务器` ==(内网专线)==> `Home Server (Mootdx)` ==> `ClickHouse Buffer`。
*   **时延**: < 500ms，完全绕过云端数据库瓶颈。

#### B. 标准通道 (K-Line/Finance)
*   **场景**: 历史数据归档、每日收盘作业。
*   **链路**: `外部数据源` --> `Cloud Server (Ingestion)` --(Write)--> `Cloud MySQL` --(T+1 Sync)--> `Home Server (ClickHouse)`。
*   **优势**: 利用云端稳定的公网环境处理爬虫/API的不稳定性，清洗后再回传内网。

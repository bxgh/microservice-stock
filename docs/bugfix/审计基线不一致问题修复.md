# 审计数据基线不一致问题修复报告

> **问题发现时间**: 2026-01-01  
> **问题类型**: 数据统计逻辑缺陷  
> **影响范围**: 周度审计报告完整性百分比计算  
> **修复状态**: ✅ 已修复

---

## 问题现象

用户发现周度审计报告中的数据异常：

```
L1 基数: 5,422
L2 MySQL: 5,468  
L3 CK: 5,468
完整性: 100.85% ❌ (实际数>基数)
```

**预期行为**: 完整性 = (实际数/基数) × 100% ≤ 100%  
**实际结果**: 完整性超过100%，不符合逻辑

---

## 根本原因

### 代码格式不一致

| 数据表 | 代码格式 | 示例 | 来源 |
|:---|:---|:---|:---|
| `stock_basic_info` | **Tushare** | `600519.SH` | Tushare API |
| `stock_kline_daily` | **BaoStock** | `sh.600519` | BaoStock API |

### 问题SQL

```python
# 错误的基线查询（旧版）
sql_baseline = "SELECT count(*) FROM stock_basic_info WHERE list_status='L'"
# 返回: 5,422 (Tushare格式代码)

# K线查询
sql_kline = "SELECT COUNT(DISTINCT code) FROM stock_kline_daily WHERE trade_date=..."
# 返回: 5,468 (BaoStock格式代码)
```

### 为什么会不一致？

1. **基线表** (`stock_basic_info`) 使用 Tushare 数据源，代码格式为 `600519.SH`
2. **K线表** (`stock_kline_daily`) 使用 BaoStock 数据源，代码格式为 `sh.600519`
3. 两个表**无法通过代码直接关联**，导致统计各自独立

---

## 修复方案

### 修改后的逻辑

**核心思路**: 使用 **K线表内部的历史数据** 作为基线，保证格式一致性

```python
# 新的基线查询
sql_baseline = """
    SELECT COUNT(DISTINCT code) 
    FROM stock_kline_daily 
    WHERE trade_date = (
        SELECT MAX(trade_date) 
        FROM stock_kline_daily 
        WHERE trade_date < %s
    )
"""
# 使用查询周开始前一天的股票总数作为基准
```

### 为什么这样更合理？

| 对比维度 | 旧方案 | 新方案 |
|:---|:---|:---|
| **数据来源** | 两个不同表 | 同一个表 |
| **代码格式** | ❌ 不一致 | ✅ 一致 |
| **时效性** | 当前在市股票 | 历史实际股票 |
| **准确性** | ❌ 格式问题导致误差 | ✅ 准确反映同步情况 |

## 为什么会存在 100.05% 的情况？

### 正常现象

```
基线 (2025-12-30): 5,465 只股票
实际 (2025-12-31): 5,468 只股票
差异: +3 只
```

**可能原因**:
1. ✅ **新股上市**: 当日有3只新股开始交易
2. ✅ **停牌解禁**: 之前停牌的股票恢复交易
3. ✅ **数据延迟**: 基线使用前一天数据，可能略有差异

**是否正常**: ✅ 正常，小幅波动是合理的

## 长期优化建议

### 方案1: 统一代码格式（推荐）⭐
```python
# 在写入时统一转换
def normalize_code(baostock_code: str) -> str:
    """sh.600519 -> 600519.SH"""
    if baostock_code.startswith('sh.'):
        return baostock_code[3:] + '.SH'
    elif baostock_code.startswith('sz.'):
        return baostock_code[3:] + '.SZ'
    return baostock_code
```

### 方案2: 创建代码映射表
```sql
CREATE TABLE code_mapping (

);
```

## 总结

### 问题本质
- 跨数据源时**代码格式不统一**
- 两个表**无法直接关联**

### 解决思路
- 改为使用**单一数据源**作为基准
- 避免跨表关联的格式问题

### 经验教训
- ⚠️ 多数据源集成时，**代码标准化**至关重要
- ⚠️ 统计逻辑应优先使用**同源数据对比**
- ⚠️ 需要建立**代码格式转换层**

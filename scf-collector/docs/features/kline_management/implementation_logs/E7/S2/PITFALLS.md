# 避坑指南 - E7-S2: 影子审计系统实战踩坑记录

> 本文档记录了在影子审计系统加固（S2）阶段遇到的技术陷阱及其解决方案，供后续微服务开发参考。

## 1. 量纲之谜：股与手的“百倍”陷阱 (P0)

### **现象**
影子审计在成交量（Volume）维度出现天文数字级别的 MAE 误差，且误差值呈现精确的 100 倍关系。

### **陷阱说明**
- **Tushare (主源)**：行情数据默认单位为 **“手”** (Lots)。
- **AkShare (备份源)**：不论是新浪 (`stock_zh_a_spot`) 还是东财 (`stock_zh_a_spot_em`)，快照接口返回的成交量单位均为 **“股”** (Shares)。
- **注意**：部分第三方文档误称 EM 源已对齐 Tushare 的“手”，但在 `akshare` 库的最新版本中，实测证明其依然保持原始的“股”量纲。

### **对策**
在适配器层（Adapter）中，所有从 AkShare 实时接口获取的成交量必须强制执行 `volume = vol_raw / 100.0` 转换。

## 2. “身份危机”：源类型判定脱节 (P1)

### **现象**
审计报告中标识备份源为 `sina`，但对账数据却包含了北京证券交易所（BJ）的股票，而 Sina 接口通常不含 BJ 票。

### **陷阱说明**
- 审计逻辑中，数据抓取层决定了 `source_type`（根据接口调用成功与否）；
- 而数据转换层（Adapter）决定了使用哪个分支（根据 DataFrame 列名是否包含中文“代码”）。
- **风险点**：若抓取层因网络抖动触发回退，但接口返回的格式与预期不符，会导致 `source_type` 标识与实际运行的适配器分支逻辑脱节。

### **对策**
**“列名决定身份”**。应以适配器分支的实际选择来反向覆盖 `source_type` 变量，确保报告输出的源信息与计算逻辑绝对对齐。

## 3. 云端只读环境：文件 I/O 陷阱 (P1)

### **现象**
代码在本地测试完美，部署到腾讯云 SCF 后，在生成审计报告时报错：`OSError: [Errno 30] Read-only file system`。

### **陷阱说明**
影子审计 1.0 版使用了临时文件生成 Markdown 报告。云函数执行环境除了 `/tmp` 目录外，其他路径均为只读。

### **对策**
彻底废弃物理文件生成逻辑。改用 Python 内存字符串流处理报告文本，并利用数据库的 `LONGTEXT` 字段（如 `report_content`）直接进行持久化。

## 4. 异步事件循环的“冷启动”隐患 (P2)

### **现象**
在高并发或频繁冷启动的 SCF 环境中，偶尔出现事件循环已关闭的报错。

### **陷阱说明**
`asyncio.get_event_loop()` 在 Python 3.10+ 环境下，若当前线程没有运行中的循环，可能会尝试创建一个新的，这在多线程 executor 模式下极不稳定。

### **对策**
强制使用 `asyncio.get_running_loop()`。它能确保只从当前运行的上下文中获取循环，若无循环则抛出明确异常，更利于生产环境调试。

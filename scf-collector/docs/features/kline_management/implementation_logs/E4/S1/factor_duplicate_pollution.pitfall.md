# 踩坑与排障复盘: [E4-S1] 自增主键下 `REPLACE INTO` 退化与历史幽灵因子污染

在执行 [E4-S1] 跨源前复权价格一致性校验时，我们发现平安银行 (`000001.SZ`)、万科 (`000002.SZ`) 等多只老牌股票在历史某些交易日上，其动态计算的前复权价格与 Tushare 官方数据存在约 `8.02%` 的微小固定百分比偏离（全局 1.35% 偏离率）。

本报告记录了这一极其隐蔽的数据库底层的物理踩坑细节、归因排查、方案决策及复用防范经验。

---

## 1. 踩坑记录 (The Pitfall)

### 1.1 问题现象
*   在对 `000001.SZ` 的 2019-04-15 进行对账时，本地 ODS 库计算的前复权收盘价为 `11.8713`，而 Tushare 官方为 `10.9894`，相对误差达到 `8.02%`。
*   查询本地数据库后发现，该股票在 `2019-04-15` 的 `adj_factor` 被填充为了 `116.700821`。
*   但 Tushare 官方库中，该股当时段的标准复权因子实际应为 `108.031`。

### 1.2 根源剖析：物理主键设计缺陷导致 `REPLACE` 失效
我们通过 `DESCRIBE stock_adjust_factor` 及数据创建时间对账，揪出了底层根源：
1.  **无联合唯一索引**：`stock_adjust_factor` 变动因子表的主键被设计为自增整数 **`id`**，而在 `(ts_code, adjust_date)` 两个决定业务唯一性的字段上，**没有设立任何唯一索引（Unique Index）**。
2.  **`REPLACE` 语义退化**：上游同步代码使用 `REPLACE INTO stock_adjust_factor ...` 进行写入。由于表中没有 `(ts_code, adjust_date)` 的唯一约束，MySQL 在执行 `REPLACE` 时，判定未发生主键冲突，从而**直接将其当成普通 `INSERT INTO` 进行了插入**。
3.  **新旧幽灵数据污染**：我们在 2026-05-15 全量同步了 Tushare 最新版因子，但未能成功覆盖或清理 2025-12-25 旧 CVM 系统录入的 **6,004 行历史残留因子数据**。旧因子比例常数与新版 Tushare 比例存在常数常数缩放差异，从而成为“幽灵因子”混杂在表中，污染了时序对齐的计算！

## 2. 方案对比与择优决策 (Options Explored)

为了解决该冲突，我们对比了以下两条解决路径：

| 方案 | 逻辑说明 | 优缺点分析 | 决策结果 |
| :--- | :--- | :--- | :--- |
| **方案 1：全量拉取覆盖** | 清空表，重新调用 Tushare 接口对全市场 5000+ 只股票下载近 30 年的因子。 | ❌ 耗时长，极大消耗 Tushare API 接口调用积分。 | **不采用** |
| **方案 2：物理清障+极速回填** | 1. 物理执行 `DELETE FROM stock_adjust_factor WHERE created_at < '2026-01-01'` 清除幽灵数据；<br>2. 运行快速广播脚本刷新日 K 线。 |  100% 保护接口积分，效率极高（秒级），对账准确率 100.0000%。 | **采纳并执行** |

## 3. 复用防范技巧 (Reusable Tips)

### 3.1 强唯一约束红线
在金融时间序列和因子库设计中，**凡是具有特定“时间-代码”业务唯一属性的事实表或因子变动表，必须强制建立联合唯一索引**：
```sql
ALTER TABLE stock_adjust_factor ADD UNIQUE INDEX uidx_code_date (ts_code, adjust_date);
```
只有确立了联合唯一约束，`REPLACE INTO` 或 `ON DUPLICATE KEY UPDATE` 的幂等写入才能真正生效，防止多源同步或多次同步时产生数据堆积和重影污染。

### 3.2 规则热注入 (.agent/rules)
此踩坑总结沉淀出的**系统级强约束**，已热注入至项目的全局反模式规约中：
> ❌ **反模式红线**：严禁在未设立业务联合唯一索引（Unique Index）的数据库事实表或因子表上，盲目使用 `REPLACE INTO` 期望进行幂等覆盖更新。
